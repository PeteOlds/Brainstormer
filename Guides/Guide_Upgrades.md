## 1. Core Architecture & Documentation

Establish the application's foundational rules, API routing, and architectural baseline in the project's baseline documents (`AGENTS.md`, supplemented by `Guardrail.md` and `PRD.md`).

* **Instruction Files:** Maintain `AGENTS.md` at the repository root to guide AI context with startup instructions, coding standards, and environment requirements.
* **Secret Management:** Store environment variables and API keys in `.env` (gitignored, never committed) with safe defaults documented in `.env.example`, and enforce strict `.gitignore` rules to keep sensitive data out of version control. Never store real secrets under `docs/` or any committed directory.
* **Environment Isolation:** Use `python -m venv venv` for local development (activate with `source venv/bin/activate`), pinning dependencies in `requirements.txt` to ensure cross-environment consistency.

## 2. Frontend Development (Flutter) **[Optional — Aspirational]**

> Applies only if/when a Flutter client is built. The current frontend is Jinja2 + Alpine.js.

Optimize the frontend for frequent, AI-assisted iterations without sacrificing stability.

* **Feature-First Structure:** Separate UI completely from business logic using robust state management (Riverpod or Bloc).
* **Repository Pattern:** Isolate all external API calls within dedicated classes to simplify mocking during automated widget tests.
* **Over-the-Air (OTA) Updates:** **[Optional]** Integrate tools like Shorebird to push non-native Dart code patches directly to users' devices, bypassing App Store review bottlenecks for daily releases.
* **Feature Flags:** **[Optional]** Utilize dark launching (e.g., PostHog) to merge half-finished features into production constantly, keeping them hidden from end users until they are fully tested.

## 3. Backend & Security (Docker & SQL)

Containerize the backend to decouple compute logic from persistent state, ensuring rapid build times and secure access.

* **Aggressive Docker Caching:** Restructure the `Dockerfile` to install dependencies in an earlier layer than the application code. This ensures subsequent builds for minor logic tweaks take seconds instead of minutes.
* **Stateless Containers:** Define infrastructure in `docker-compose.yml` and map all databases, logs, and user uploads to external volumes or bind mounts.
* **Row Level Security (RLS):** **[Optional — Postgres/Supabase projects only.]** Where the database supports it, implement RLS to guarantee users can only access their specific records, creating a database-layer failsafe against application authorization bugs. (BS: SQLite has no RLS — Brainstormer enforces isolation in server-side auth checks per `Guardrail.md`. Do not generate RLS policies for the SQLite path.)
* **Payload Validation:** Sanitize all incoming requests at the initial routing layer before they hit the business logic to prevent injection attacks.

## 4. Zero Data Loss Upgrades

Safely iterating the database multiple times a day requires decoupling schema changes from the application lifecycle.

* **Expand-and-Contract Migrations:** Never drop columns or tables in a single step on populated production tables. Add new columns (expand), deploy code that writes to both, and drop the old columns (contract) only when the new feature is stable. (BS: Alembic via `flask db migrate` — always review autogenerated scripts, verify `upgrade` and `downgrade` in CI, and never run `db.create_all()` in production.)
* **Declarative Schema Diffing:** **[Optional]** Use tools like the Supabase CLI or Atlas to define the desired end-state schema and automatically generate the step-by-step SQL required to safely transition the production database.
* **Database Branching:** Configure the CI/CD pipeline to spin up ephemeral, isolated copies of the production database schema. Run automated tests against this branch to prove migrations will not cause data loss before deploying to the live containers.

## 5. Automated Rollback Strategies

When high-frequency deployments fail in the live environment, instant remediation is required.

* **Container Tag Reversion:** Never use the `:latest` Docker tag. Deploy specific version hashes. If post-deployment health checks fail, the orchestrator or CI pipeline must automatically update the deployment file to the previous working tag and recreate the containers.
* **OTA Patch Rollback:** **[Optional — Shorebird projects only.]** If a frontend bug slips through, utilize Shorebird's console to instantly revoke the latest patch, reverting users to the previous stable Dart build on their next app launch.
* **Roll-Forward Prioritization (Data):** True database rollbacks often cause data loss. Because the system utilizes the expand-and-contract pattern, a failed deployment during the "expand" phase allows you to simply revert the application containers; the old code will safely ignore the new, unused database columns while you fix the bug and roll forward. Down-migration scripts (per `Guide_Database.md` §3) remain mandatory as a development/CI safety net — they are not the production recovery strategy.
* **Snapshot Restoration Drills:** Take automated logical backups before every deployment. Maintain a documented, tested restore procedure for the active containers and database, and schedule routine drills to prove it works. Prefer point-in-time restore and roll-forward; reserve destroy-and-rebuild-from-snapshot for declared disasters, and rehearse it before you need it.
